# TaskNotes: key features and technical design

Verified **3 October 2026** against **TaskNotes 4.13.8** (release tag and manifest, source commit [`1ba391b`](https://github.com/callumalpass/tasknotes/tree/1ba391b957c6fbbdc484716bbc5a284f5f02e59d)). Its [manifest](https://github.com/callumalpass/tasknotes/blob/1ba391b957c6fbbdc484716bbc5a284f5f02e59d/manifest.json) requires **Obsidian 1.12.2 or later**; the **Bases** core plugin must be enabled for the main task views. Sources: the official [documentation](https://tasknotes.dev/), [project overview (README)](https://github.com/callumalpass/tasknotes/blob/1ba391b957c6fbbdc484716bbc5a284f5f02e59d/README.md), [4.13.8 release notes](https://github.com/callumalpass/tasknotes/blob/1ba391b957c6fbbdc484716bbc5a284f5f02e59d/docs/releases/4.13.8.md), and linked source files below. This is a documentation and source inspection, not a hands-on test in a live vault; optional service integrations were not connected.

TaskNotes adds task management to an Obsidian vault (a folder of notes). Each task is an ordinary Markdown file (plain text with simple formatting symbols): YAML *frontmatter* (properties written as plain text between `---` lines) holds task data, and the body holds freeform notes. Obsidian Bases, a built-in tool for querying notes, turns those files into filtered views; TaskNotes adds task-specific controls and actions. [Core concepts](https://tasknotes.dev/core-concepts/).

## Capture, edit, and organise

**Task capture.** Create a task with Obsidian's command menu, side toolbar, task creation window, calendar, or a view's add control. The creation window supports both quick text entry and direct property editing with a details editor; quick actions change common fields without opening the file. The text-entry mechanism is explained in **Natural-language task input** below. [Task management](https://tasknotes.dev/features/task-management/), [inline input](https://tasknotes.dev/features/inline-tasks/#natural-language-processing). (Verified v4.13.8.)

**Inline conversion.** A command or editor button can turn a checkbox, list item, heading, quote, or plain line into a separate task note and replace the source text with a task link. A bulk command converts all checkbox tasks in the current note; another command creates a new task and inserts its link. Linked tasks can appear as interactive status/date/priority widgets in Obsidian's Live Preview and Reading mode, with a configurable display. [Inline tasks](https://tasknotes.dev/features/inline-tasks/). (Verified v4.13.8.)

**Task relationships.** A task can belong to several project notes; any note can act as a project, and a task can itself be a project with subtasks. A relationships panel shows projects, subtasks, tasks that block one another, and separate notes for individual repeats where relevant. Task menus can create a linked subtask or select blocking tasks. [Task management](https://tasknotes.dev/features/task-management/#projects), [relationships widget](https://tasknotes.dev/features/inline-tasks/#relationships-widget). (Verified v4.13.8.)

**Workflow states.** Statuses and priorities have configurable stored values, display labels, colours, and order. Each status has a true/false setting for whether it counts as completed; TaskNotes does not decide this from a word such as `done`. Status clicks can cycle through a configurable sequence. Completion menus can record today, scheduled date, due date, or a chosen date, and statuses can be marked archived automatically after a configured delay. [Task properties](https://tasknotes.dev/settings/task-properties/), [completion and archiving](https://tasknotes.dev/features/task-management/#completing-tasks). (Verified v4.13.8.)

**Templates and fields.** New task bodies, folders, and filenames can use templates with variables such as `{{title}}`, `{{date}}`, and `{{project}}`; filename formats include title, date-based identifier, timestamp (date-and-time code), UUID (universally unique identifier, a random-looking ID), and custom template. Users can add typed fields (text, number, Boolean or true/false, date, list) for forms, filtering, sorting, and grouping. Defaults, visible task-form fields, storage folders, task-card display, and property names are separately configurable. [Template variables](https://tasknotes.dev/features/template-variables/), [user fields](https://tasknotes.dev/features/user-fields/), [settings](https://tasknotes.dev/settings/). (Verified v4.13.8.)

## Natural-language task input

This expands the **Task capture** entry above. Natural-language input means typing a task description that mixes ordinary words with dates, labels, or short commands for task properties. It is enabled by default in the task creation window, where a preview updates as you type; saving parses the text if you have not already entered a separate title, and **Fill from natural language** can copy parsed values into the detailed form for review. Instant conversion can also use the parser when enabled. A separate parse-only API (application programming interface, a way for software to request results) returns the interpreted values without creating a file. [Inline tasks](https://tasknotes.dev/features/inline-tasks/#natural-language-processing), [feature settings](https://tasknotes.dev/settings/features/#natural-language-processing), [modal source](https://github.com/callumalpass/tasknotes/blob/1ba391b957c6fbbdc484716bbc5a284f5f02e59d/src/modals/TaskCreationModal.ts), [NLP API](https://tasknotes.dev/nlp-api/). (Verified v4.13.8.)

The parser works on the **first line** of input; later lines become freeform task details. It checks that first line in stages for tags, contexts, projects, priority, status, repeat pattern, time estimate, custom fields, and dates/times. Recognised pieces are removed, and the remaining words become the task title; an unrecognised piece stays in the title. This can also consume an ordinary title word if it matches a configured status or priority. Double quotes, single quotes, or backticks can protect a phrase such as `"Today"` from being read as a date or estimate. This first-line rule and staged removal are verified in the [shared parser source](https://github.com/callumalpass/tasknotes-nlp-core/blob/c2aa287cd0eae4a0e2c451570402d3fa1ecdaec0/src/NaturalLanguageParserCore.ts); [literal-text guidance](https://tasknotes.dev/settings/features/#natural-language-processing) is documented. (Verified v4.13.8 with the plugin's locked parser v0.1.5.)

Default *triggers* are characters that mark the next value. `#writing` adds a tag (category label), while `@desk` adds a context (place or situation label). `+[[Project Alpha]]` adds a linked project using Obsidian's `[[...]]` note-link syntax; `+project` accepts a simple project name. TaskNotes can also recognise configured status and priority labels or stored values as plain words. The default status trigger `*` is enabled; the default priority trigger `!` is disabled, but turning off either trigger does not stop plain-word matching. `2h`, `30min`, and `1h30m` become estimates in minutes, while `daily` and `every Monday` become repeat rules. A configured custom field can use its own trigger, such as `effort: "very high"`. Triggers can be changed or disabled on **Settings → Task Properties**. [Inline syntax and triggers](https://tasknotes.dev/features/inline-tasks/#natural-language-processing), [trigger settings source](https://github.com/callumalpass/tasknotes/blob/1ba391b957c6fbbdc484716bbc5a284f5f02e59d/src/settings/tabs/taskProperties/helpers.ts), [default trigger settings](https://github.com/callumalpass/tasknotes/blob/1ba391b957c6fbbdc484716bbc5a284f5f02e59d/src/settings/defaults.ts), [parser source](https://github.com/callumalpass/tasknotes-nlp-core/blob/c2aa287cd0eae4a0e2c451570402d3fa1ecdaec0/src/NaturalLanguageParserCore.ts). (Verified v4.13.8.)

Date words are interpreted using the chosen **natural-language processing (NLP) language** (the language of recognised phrases and date patterns), English by default. An explicit phrase such as `due tomorrow at 3pm` targets `due`, while `scheduled for Friday` targets `scheduled`; both dates can be supplied in one entry. A bare date such as `tomorrow` goes to `scheduled` by default, or to `due` if **Default to scheduled** is turned off. A recognised time is joined to its date, for example as `YYYY-MM-DDTHH:mm` (year-month-day, then hour:minute); numeric date order also depends on the configured calendar language-and-region setting or the device/browser language-and-region setting. This matters because a relative word changes meaning with the day of entry, and an unlabelled date does not always mean a deadline. [NLP settings](https://tasknotes.dev/settings/features/#natural-language-processing), [NLP API](https://tasknotes.dev/nlp-api/), [plugin parser adapter](https://github.com/callumalpass/tasknotes/blob/1ba391b957c6fbbdc484716bbc5a284f5f02e59d/src/services/NaturalLanguageParser.ts), [date parser source](https://github.com/callumalpass/tasknotes-nlp-core/blob/c2aa287cd0eae4a0e2c451570402d3fa1ecdaec0/src/NaturalLanguageParserCore.ts). (Verified v4.13.8.)

For example, with default triggers, typing **`Draft outline #writing @desk +[[Project Alpha]]`** yields the parsed title **`Draft outline`**, tag **`writing`**, context **`desk`**, and project link **`[[Project Alpha]]`**. On creation, TaskNotes writes these to the configured `tags`, `contexts`, and `projects` frontmatter fields and adds its separate identifying `task` tag in default recognition mode; status and priority come from defaults unless supplied. Parsed `2h` would become `timeEstimate: 120`, a custom field uses its configured frontmatter key, and a recurrence phrase becomes a stored recurrence rule. The exact filename and whether `title` is also written to frontmatter depend on title settings. [Parser source](https://github.com/callumalpass/tasknotes-nlp-core/blob/c2aa287cd0eae4a0e2c451570402d3fa1ecdaec0/src/NaturalLanguageParserCore.ts), [parsed-data mapping](https://github.com/callumalpass/tasknotes/blob/1ba391b957c6fbbdc484716bbc5a284f5f02e59d/src/services/buildTaskCreationDataFromParsed.ts), [creation source](https://github.com/callumalpass/tasknotes/blob/1ba391b957c6fbbdc484716bbc5a284f5f02e59d/src/services/task-service/TaskCreationService.ts). (Verified v4.13.8; example shows parsed values, not a complete saved file.)

## Views and scheduling

**Bases task views.** Task List filters, sorts, groups, and offers persistent manual drag ordering. Kanban is a board of task cards arranged in columns and optional rows; dragging a card can change its grouped property. Views use editable `.base` files (Obsidian view-definition files), so saved filters and layouts are vault files rather than hidden view records; a current migration action can export older saved views to a multi-view Base file. [Task List](https://tasknotes.dev/views/task-list/), [Kanban](https://tasknotes.dev/views/kanban-view/), [view migration](https://tasknotes.dev/migration-v3-to-v4/#converting-saved-filter-views). (Verified v4.13.8.)

**Calendar planning.** Calendar offers month, week, day, year, list, and configurable multi-day modes; Agenda is a separate default `.base` file using calendar list mode. Tasks can be created or rescheduled by date/time clicks and drags; display options include due, scheduled, recurrence, tracked time, time blocks, and external events. Mini Calendar gives a compact coloured date overview and navigation and can use a date property beyond tasks. [Calendar](https://tasknotes.dev/views/calendar-views/), [Agenda](https://tasknotes.dev/views/agenda-view/). (Verified v4.13.8.)

**Recurring tasks.** A rule defines when a task repeats while `scheduled` records the next planned date; individual dates can be completed or skipped. Dragging the next planned task on the calendar changes that date. Dragging a date shown only by the repeat rule changes the rule's starting point. A repeat needing its own notes, checklist, status, or time entries can become a separate task note; the parent can optionally create the next such note on completion or skip. [Recurrence](https://tasknotes.dev/features/recurring-tasks/). (Verified v4.13.8.)

**Reminders and time.** Reminders can be set for exact dates and times or for periods before or after a task's due/scheduled date, with in-app or system notification settings; delivery requires Obsidian to be running. Per-task time tracking records start/stop sessions, and the calendar can edit them; a Pomodoro view runs timed work and break intervals with history and statistics. Optional time blocks instead live in daily notes and represent planned time, rather than actual tracked time. [Reminders](https://tasknotes.dev/features/reminders/), [time management](https://tasknotes.dev/features/time-management/), [time blocking](https://tasknotes.dev/settings/features/#timeblocking). (Verified v4.13.8.)

**Calendar connections.** Google Calendar and Microsoft Outlook connections use OAuth (account-authorised sign-in) and can show and change external events; ICS (a common calendar-file format) subscriptions show read-only feeds. TaskNotes can create or link notes/tasks from ICS events and export tasks to an ICS file; Google task export is separately configurable. These integrations require setup and have provider-specific behaviour. [Calendar integration](https://tasknotes.dev/features/calendar-integration/), [ICS integration](https://tasknotes.dev/features/ics-integration/), [integration settings](https://tasknotes.dev/settings/integrations/). (Verified v4.13.8.)

**Automation access.** Commands cover creation, conversion, view opening, status/priority changes, timing, refresh, and calendar export/sync. Optional desktop-only local web (HTTP, the standard for web requests) and Model Context Protocol (MCP, a standard for tool connections) interfaces allow authorised external programs to work with tasks; webhooks send automatic web messages to other systems about selected changes. A JavaScript API inside Obsidian supports companion plugins, while the separate browser extension and CLI (command-line tool) are clients of TaskNotes rather than task storage. [Commands in source](https://github.com/callumalpass/tasknotes/blob/1ba391b957c6fbbdc484716bbc5a284f5f02e59d/src/commands/taskNotesCommands.ts), [HTTP API](https://tasknotes.dev/HTTP_API/), [webhooks](https://tasknotes.dev/webhooks/), [companion plugins](https://tasknotes.dev/companion-plugins/). (Verified v4.13.8.)

## Task recognition

This expands the original **Task recognition** entry. By default, TaskNotes checks a Markdown file's YAML **frontmatter** (the property block between `---` lines) for its `tags` property. The default identifying value is `task`: both `tags: task` and `tags: [task]` work. The `#` belongs to tag notation in ordinary Markdown text; the normal YAML value is `task` without `#`, although the plugin's tag-cleanup code also strips one leading `#` from a frontmatter value. It accepts an exact tag or a slash-separated child such as `task/project`, without regard to letter case; `tasking` is not a child of `task`. [General settings](https://tasknotes.dev/settings/general/#task-identification), [frontmatter tag normalisation](https://github.com/callumalpass/tasknotes/blob/1ba391b957c6fbbdc484716bbc5a284f5f02e59d/src/utils/taskIdentificationFrontmatter.ts), [tag matching source](https://github.com/callumalpass/tasknotes/blob/1ba391b957c6fbbdc484716bbc5a284f5f02e59d/src/utils/FilterUtils.ts). (Verified v4.13.8.)

For the plugin's own task reader, `tags: [task/project]` in frontmatter is enough; `tags: [tasking]` is not, even if the note body contains `#task`. The reader does **not** use body text, task-like checkboxes, a `Tasks` folder, filename, or a `status` property as substitutes for the configured identifier. Its task-tag value is configurable, so `task` is the default rather than a universal rule. These boundaries come directly from the [recognition function](https://github.com/callumalpass/tasknotes/blob/1ba391b957c6fbbdc484716bbc5a284f5f02e59d/src/utils/taskIdentification.ts) and [default settings](https://github.com/callumalpass/tasknotes/blob/1ba391b957c6fbbdc484716bbc5a284f5f02e59d/src/settings/defaults.ts). (Verified v4.13.8.)

Alternatively, **Identify tasks by → Property** *replaces* tag recognition with a named frontmatter property and expected value, for example `isTask: true` or `category: task`; a tag is then unnecessary. The value can be a single item or a list, and a list matches if **any** item equals the configured value. If the setting says `true` or `false`, a real YAML Boolean (true/false value), such as `isTask: true`, matches; `isTask: false` does not match a configured `true`. Other values must match exactly, including capitalisation; property mode does not gain tag mode's child-tag rule even if its chosen property is `tags`. If either setting is blank, no files qualify in property mode—merely having the property is not enough. [Property identification](https://tasknotes.dev/settings/property-identification/), [general settings](https://tasknotes.dev/settings/general/#task-identification), [recognition source](https://github.com/callumalpass/tasknotes/blob/1ba391b957c6fbbdc484716bbc5a284f5f02e59d/src/utils/taskIdentification.ts). (Verified v4.13.8.)

TaskNotes scans Markdown files in the vault and reads Obsidian's **metadata cache** (Obsidian's stored reading of note properties) to apply the chosen rule; excluded folders are skipped. It listens for note metadata changes, deletion, and renames, so a frontmatter edit can cause a note to enter or leave the task set without moving the file. New tasks get the currently configured identifier written at creation. The `.base` view files have their own saved filters: changing the identification setting does not rewrite existing views, so those filters may need updating separately. [TaskManager source](https://github.com/callumalpass/tasknotes/blob/1ba391b957c6fbbdc484716bbc5a284f5f02e59d/src/utils/TaskManager.ts), [creation source](https://github.com/callumalpass/tasknotes/blob/1ba391b957c6fbbdc484716bbc5a284f5f02e59d/src/services/task-service/TaskCreationService.ts), [general settings](https://tasknotes.dev/settings/general/#views--base-files). (Verified v4.13.8.)

## Task file structure and compatibility

**Minimum task shape.** Other task fields are optional for recognition once the configured identifier is present. The default new-task folder is `TaskNotes/Tasks`; it is configurable and is not itself an identifier. Title can come from the filename or mapped `title` field; if cleaning a filename or resolving a duplicate name would lose the full title, TaskNotes keeps it in frontmatter. While the plugin runs, a task's `id` is its vault file path, so renaming or moving changes that path; UUID/timestamp filename modes are filename strategies, not mandatory frontmatter task IDs. [Core concepts](https://tasknotes.dev/core-concepts/), [title settings](https://tasknotes.dev/settings/task-properties/#title), [creation source](https://github.com/callumalpass/tasknotes/blob/1ba391b957c6fbbdc484716bbc5a284f5f02e59d/src/services/task-service/TaskCreationService.ts), [task assembly source](https://github.com/callumalpass/tasknotes/blob/1ba391b957c6fbbdc484716bbc5a284f5f02e59d/src/utils/taskInfoAssembly.ts). (Verified v4.13.8.)

**Default property names.** TaskNotes uses these frontmatter keys by default:

- Task labels and links: `title`, `status`, `priority`, `tags`, `contexts`, `projects`, `attachments`, `blockedBy`.
- Dates and plans: `due`, `scheduled`, `completedDate`, `dateCreated`, `dateModified`, `timeEstimate`, `recurrence`, `recurrence_anchor`, `reminders`.
- History and order: `complete_instances`, `skipped_instances`, `timeEntries`, and `tasknotes_manual_order` (manual position in a list).

Default statuses are `none`, `open`, `in-progress`, `done` (`done` is completed); priorities are `none`, `low`, `normal`, `high`. A new task normally starts with `status: open`, `priority: normal`, and a scheduled date of today unless the user changes the defaults. Except for native `tags`, core property names can be changed in settings; this does not rename properties in existing files. [Property types](https://tasknotes.dev/settings/property-types-reference/), [property settings](https://tasknotes.dev/settings/task-properties/), [mapping source](https://github.com/callumalpass/tasknotes/blob/1ba391b957c6fbbdc484716bbc5a284f5f02e59d/src/core/defaultFieldMapping.ts), [defaults source](https://github.com/callumalpass/tasknotes/blob/1ba391b957c6fbbdc484716bbc5a284f5f02e59d/src/settings/defaults.ts). (Verified v4.13.8.)

**Dates and lists.** `due` and `scheduled` accept `YYYY-MM-DD` or a date and time such as `YYYY-MM-DDTHH:mm` (year-month-day, then hour:minute); `completedDate` is a date, while `dateCreated`/`dateModified` are timestamps. `contexts`, `projects`, `tags`, `complete_instances`, and `skipped_instances` are lists; `timeEstimate` is a number of minutes. Projects are usually quoted Obsidian links such as `"[[Project Alpha]]"`; Markdown links in frontmatter require an optional companion plugin setting. A project is a linked note, not a separate project database. [Property types](https://tasknotes.dev/settings/property-types-reference/), [general settings](https://tasknotes.dev/settings/general/#frontmatter), [projects](https://tasknotes.dev/features/task-management/#projects). (Verified v4.13.8.)

**Repeat rule.** `recurrence` stores a calendar-standard repeat rule, for example `"DTSTART:20250804;FREQ=WEEKLY;BYDAY=MO"`. Here `DTSTART` sets the starting date (4 August 2025), `FREQ=WEEKLY` means repeat weekly, and `BYDAY=MO` selects Monday. `scheduled` separately stores the next planned date; `recurrence_anchor` selects whether the next repeat is calculated from that date or from completion. `complete_instances` and `skipped_instances` list dates in `YYYY-MM-DD` form. [Recurrence](https://tasknotes.dev/features/recurring-tasks/), [property types](https://tasknotes.dev/settings/property-types-reference/#materialized-occurrence-properties). (Verified v4.13.8.)

**Separate repeat notes.** A task note created for one repeat stores `recurrence_parent` (link/path to the parent) and `occurrence_date` (its original date). The parent can set `occurrence_materialization` to `manual` or `on_completion`; when automatic creation is enabled, `occurrence_next_trigger` controls whether skipping a repeat also creates the next note. `occurrence_template` names an optional template for these notes. [Recurrence](https://tasknotes.dev/features/recurring-tasks/), [property types](https://tasknotes.dev/settings/property-types-reference/#materialized-occurrence-properties). (Verified v4.13.8.)

**Time entries.** `timeEntries` lists work sessions. Each entry requires `startTime`; optional `endTime` and `description` add the stop time and notes. No end time means a session is still running. [Property types](https://tasknotes.dev/settings/property-types-reference/#complex-properties). (Verified v4.13.8.)

**Blocking relationships.** Each `blockedBy` entry has `uid` (usually a task link/path), `reltype` (relationship type), and optional `gap` (a standard duration such as `P1D` for one day). The task controls write `FINISHTOSTART` (a finish-to-start relationship label). Other accepted relationship names do not currently change scheduling differently. [Property types](https://tasknotes.dev/settings/property-types-reference/#complex-properties), [dependencies](https://tasknotes.dev/features/task-management/#dependencies). (Verified v4.13.8.)

**Reminder records.** Each `reminders` entry has an `id`. A reminder can use `type: relative`, `relatedTo: due` or `relatedTo: scheduled`, and an `offset` before or after that date; for example, `-PT1H` means one hour before. Alternatively, `type: absolute` uses `absoluteTime` for a fixed date and time. [Property types](https://tasknotes.dev/settings/property-types-reference/#complex-properties), [reminders](https://tasknotes.dev/features/reminders/#reminder-data-format). (Verified v4.13.8.)

**Archive and order.** Archiving adds the configured archive tag, by default `archived`, to `tags`; optionally it moves the file to the archive folder (default `TaskNotes/Archive`, move disabled by default). Manual ordering stores LexoRank-style values (sortable position codes) in the configured property, default `tasknotes_manual_order`, when the view sorts by that field. These are task-file changes, while which properties are shown and how they are filtered live in each `.base` file. [Archive source](https://github.com/callumalpass/tasknotes/blob/1ba391b957c6fbbdc484716bbc5a284f5f02e59d/src/services/task-service/taskArchivePlanning.ts), [mapping source](https://github.com/callumalpass/tasknotes/blob/1ba391b957c6fbbdc484716bbc5a284f5f02e59d/src/core/defaultFieldMapping.ts), [file defaults](https://tasknotes.dev/settings/task-defaults/), [list ordering](https://tasknotes.dev/views/task-list/#drag-to-reorder). (Verified v4.13.8.)

## How TaskNotes runs and stores data

**Bases files — source verified.** Default views are `.base` files in `TaskNotes/Views/`; their filters select task files, and custom view types are `tasknotesTaskList`, `tasknotesKanban`, `tasknotesCalendar`, and `tasknotesMiniCalendar`. The default tag filter uses `file.hasTag("task")` (an Obsidian query for that tag); property mode generates a matching property filter. Changing identification or field mapping does not automatically rewrite already-created `.base` files: use the explicit update action or edit them. Bases supplies matching, grouping, sorting, and note property values; TaskNotes renders task controls and handles actions. [Bases templates source](https://github.com/callumalpass/tasknotes/blob/1ba391b957c6fbbdc484716bbc5a284f5f02e59d/src/templates/defaultBasesFiles.ts), [Bases adapter source](https://github.com/callumalpass/tasknotes/blob/1ba391b957c6fbbdc484716bbc5a284f5f02e59d/src/bases/BasesDataAdapter.ts), [general settings](https://tasknotes.dev/settings/general/#views--base-files). (Verified v4.13.8.)

**Reads and writes — source verified.** `TaskManager` reads Obsidian's metadata cache (Obsidian's parsed note information), scans Markdown files for all-task operations, maintains small lookup lists for filters, and listens for metadata changes, deletion, and vault renames. Task creation uses Obsidian's vault file API (its programming interface for files); updates edit the frontmatter and file contents, with the file manager handling renames. It also sends change notices so cards and views refresh after edits made in Obsidian itself. [TaskManager source](https://github.com/callumalpass/tasknotes/blob/1ba391b957c6fbbdc484716bbc5a284f5f02e59d/src/utils/TaskManager.ts), [creation source](https://github.com/callumalpass/tasknotes/blob/1ba391b957c6fbbdc484716bbc5a284f5f02e59d/src/services/task-service/TaskCreationService.ts), [update source](https://github.com/callumalpass/tasknotes/blob/1ba391b957c6fbbdc484716bbc5a284f5f02e59d/src/services/task-service/TaskUpdateService.ts). (Verified v4.13.8.)

**Storage boundaries.** Task data, including recurrence history and time entries, resides in Markdown files; default view definitions reside in `.base` files. Plugin settings and some operational data, including plugin-stored Pomodoro history, reside in `.obsidian/plugins/tasknotes/data.json`; Pomodoro history can instead be written to daily-note frontmatter. Calendar sign-in secrets and access tokens (keys that authorise access) use Obsidian Secret Storage, separate from `data.json`. Thus “no plugin-specific database” describes the task store, not an absence of plugin settings or temporary in-memory lookup data. [Backup guide](https://tasknotes.dev/guides/backup-recovery/), [Pomodoro settings](https://tasknotes.dev/settings/features/#pomodoro-timer), [calendar storage](https://tasknotes.dev/features/calendar-integration/#token-management). (Verified v4.13.8.)

**Architecture boundary.** The plugin's startup code starts components and registers commands. Other components create and edit tasks, handle repeat schedules and filters, and connect outside services; adapters (translation code) turn Obsidian note and Bases data into task records. Views and task windows display those records and call the task components when users act. This separation helps explain how the `.md` task files and `.base` view files work apart from the screen controls. [Architecture notes](https://github.com/callumalpass/tasknotes/blob/1ba391b957c6fbbdc484716bbc5a284f5f02e59d/docs/development/architecture.md), [bootstrap source](https://github.com/callumalpass/tasknotes/blob/1ba391b957c6fbbdc484716bbc5a284f5f02e59d/src/bootstrap/pluginBootstrap.ts). (Verified v4.13.8.)

## Evidence limits and documented discrepancies

- The [README's short task examples](https://github.com/callumalpass/tasknotes/blob/1ba391b957c6fbbdc484716bbc5a284f5f02e59d/README.md#task-structure) omit the default identifying `tags: [task]`; they illustrate properties, but are not complete default-mode task files. The source recognition rule and [core-concepts example](https://tasknotes.dev/core-concepts/#task-structure) resolve this.
- The README's short recurrence example omits `DTSTART` (the repeat pattern's starting date, explained above). The [recurrence guide](https://tasknotes.dev/features/recurring-tasks/#backward-compatibility) says older rules without it remain readable, while current task creation [adds it](https://github.com/callumalpass/tasknotes/blob/1ba391b957c6fbbdc484716bbc5a284f5f02e59d/src/services/task-service/TaskCreationService.ts). The README example is therefore shorter than a newly written rule.
- [ICS integration documentation](https://tasknotes.dev/features/ics-integration/#content-type-detection) says its related-content task/note label checks the task tag. This matches the [ICS modal source](https://github.com/callumalpass/tasknotes/blob/1ba391b957c6fbbdc484716bbc5a284f5f02e59d/src/modals/ICSEventInfoModal.ts), but differs from the main reader's property-mode task recognition; a property-identified task without the tag may therefore be labelled a note in that modal. This is a narrow display difference, not a change to task discovery.
- The separate [TaskNotes specification](https://tasknotes.dev/developers/specification/09-configuration/#97-task_detection-schema) describes inline body `#task` recognition and matching a property merely because it exists when the expected value is blank. The Obsidian plugin's [current recognition source](https://github.com/callumalpass/tasknotes/blob/1ba391b957c6fbbdc484716bbc5a284f5f02e59d/src/utils/taskIdentification.ts) does neither. The sections above describe the plugin's observed source behaviour, not the broader cross-tool specification.
- The [TaskNotes specification](https://github.com/callumalpass/tasknotes-spec) describes data conventions for more than one tool. This reference records verified plugin 4.13.8 behaviour; it does not claim the plugin follows every part of that specification, test other tools, or cover invalid YAML notes.
- The [inline input guide](https://tasknotes.dev/features/inline-tasks/#natural-language-processing) locates **NLP Triggers** under **Features**, while the current [settings UI source](https://github.com/callumalpass/tasknotes/blob/1ba391b957c6fbbdc484716bbc5a284f5f02e59d/src/settings/tabs/taskProperties/helpers.ts) places trigger controls for each property under **Task Properties**. The navigation above follows the plugin source.
- **Assumptions:** None about undocumented TaskNotes behaviour. Examples use the verified default settings; a vault with remapped fields, statuses, or task identification can store different values.
