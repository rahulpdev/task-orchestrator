# TaskNotes Workflows: key features and technical design

**Verification (4 October 2026).** I reviewed TaskNotes Workflows **0.1.4**, the latest GitHub release not marked as a preview ([release](https://github.com/callumalpass/tasknotes-workflows/releases/tag/0.1.4); [manifest](https://github.com/callumalpass/tasknotes-workflows/blob/0.1.4/manifest.json)). It needs Obsidian **1.8.0+** and TaskNotes' JavaScript API, which lets other plugins read and change tasks; it names no minimum TaskNotes version. The TaskNotes version checked, **4.13.8**, needs Obsidian **1.12.2+** and Bases, Obsidian's tool for showing notes as tables or cards ([manifest](https://github.com/callumalpass/tasknotes/blob/4.13.8/manifest.json)). Sources: Workflows [README](https://github.com/callumalpass/tasknotes-workflows/blob/0.1.4/README.md), [format guide](https://github.com/callumalpass/tasknotes-workflows/blob/0.1.4/docs/workflow-schema.md), and [0.1.4 code](https://github.com/callumalpass/tasknotes-workflows/tree/0.1.4/src); TaskNotes [API guide](https://github.com/callumalpass/tasknotes/blob/4.13.8/docs/javascript-api.md) and [task guide](https://github.com/callumalpass/tasknotes/blob/4.13.8/docs/features/task-management.md); and Obsidian's [Bases guide](https://docs.obsidian.md/plugins/guides/bases-view). I did not test the plugin in a live Obsidian vault (a folder of notes), Base rendering, or permissions between apps. **Assumption:** “stable” means the latest release not marked as a preview.

TaskNotes Workflows is an optional automation companion to TaskNotes. A **workflow** is a saved rule that reacts to a task event, a schedule, or a manual run, then performs actions in order. TaskNotes stores and manages the task notes; Workflows stores the rules, starts runs, and records what happened. A run does not add a lasting record to its tasks or automatically group them. [Documented and source verified: [README](https://github.com/callumalpass/tasknotes-workflows/blob/0.1.4/README.md), [engine](https://github.com/callumalpass/tasknotes-workflows/blob/0.1.4/src/workflowEngine.ts), [steps](https://github.com/callumalpass/tasknotes-workflows/blob/0.1.4/src/stepRegistry.ts).]

## User-facing functionality

**Workflow view.** By default, workflow notes go in `TaskNotes/Workflows/`, and the plugin creates `TaskNotes/Views/workflows.base`. This Base shows each workflow's status, triggers, steps, and latest run as cards. A card lets users edit, open, run, or dry-run a workflow; a dry run tests it without saving task or file changes. Workflow notes can also show a compact card in Obsidian's editor or reading view. A toolbar icon opens the Base; commands include **Open workflows**, **New workflow**, **Reload workflows**, **Maintain default workflow files**, and **Migrate workflow files to the mdbase runtime format**. [0.1.4; [README](https://github.com/callumalpass/tasknotes-workflows/blob/0.1.4/README.md), [commands](https://github.com/callumalpass/tasknotes-workflows/blob/0.1.4/main.ts#L317), [Base view](https://github.com/callumalpass/tasknotes-workflows/blob/0.1.4/src/workflowBasesView.ts).]

**Workflow authoring.** Users can edit a workflow in a form or change its Markdown note, a plain-text file, directly. The form shows triggers, conditions, actions, run limits, and their inputs, while reading status and priority choices from TaskNotes. It also offers fixed dates, values from a run, relative dates, and formulas, which are small calculations stored as `{ $expr: "..." }`. The form edits YAML frontmatter, a plain-text block of named settings at the top of the note, and keeps the explanatory body. [0.1.4; [README](https://github.com/callumalpass/tasknotes-workflows/blob/0.1.4/README.md), [editor](https://github.com/callumalpass/tasknotes-workflows/blob/0.1.4/src/workflowEditModal.ts), [repository](https://github.com/callumalpass/tasknotes-workflows/blob/0.1.4/src/workflowRepository.ts).]

**Starter examples.** The plugin can create disabled example workflows on first load. They cover time tracking, dates, overdue and blocked tasks, moving completed tasks, and copying or mirroring information between parent tasks and subtasks. Other examples show a canvas action through another app and scheduling subtasks before a parent's due date. The **Maintain default workflow files** command adds missing examples without replacing edited ones. [0.1.4; [defaults](https://github.com/callumalpass/tasknotes-workflows/blob/0.1.4/src/defaultWorkflowsService.ts), [changelog](https://github.com/callumalpass/tasknotes-workflows/blob/0.1.4/CHANGELOG.md).]

**Trigger choices.** A workflow can have several triggers, or events that start it. Choices include TaskNotes changes such as `task.status.changed`, a cron schedule (a five-part time rule), a repeating interval, a manual command, and selected Obsidian file, property, or workspace events. It can also react to a contract event, a message from another app with an agreed name and version. TaskNotes triggers can check the old and new status, task path, and whether to react to the workflow's own writes. Obsidian event triggers start off disabled; an enabled manual workflow gets a `Run: <workflow name>` command with ID `run-workflow-<workflow id>`. [0.1.4; [schema guide](https://github.com/callumalpass/tasknotes-workflows/blob/0.1.4/docs/workflow-schema.md), [scheduler](https://github.com/callumalpass/tasknotes-workflows/blob/0.1.4/src/scheduler.ts), [commands](https://github.com/callumalpass/tasknotes-workflows/blob/0.1.4/main.ts#L401).]

**Task actions.** Workflows can find and read tasks, create them, change their fields, move or archive them, and mark them complete or open. Other actions manage dates, tags, projects, contexts, dependencies, and time entries. A task search uses TaskNotes' query API: a request that names which tasks to find. Workflows sends changes through the TaskNotes API, and TaskNotes writes the notes using its own settings. The form shows common `task.create` fields; a workflow note can provide more fields that TaskNotes accepts. [0.1.4; [step catalog](https://github.com/callumalpass/tasknotes-workflows/blob/0.1.4/src/stepRegistry.ts#L200), [TaskNotes API](https://github.com/callumalpass/tasknotes/blob/4.13.8/docs/javascript-api.md).]

**Relationship actions.** The read actions `task.parents`, `task.subtasks`, `task.dependencies`, `task.blocking`, and `task.relationships` ask TaskNotes to find related task notes. `task.addDependency` and `task.removeDependency` change blockers, which are tasks that must be finished first. `task.addProject` and `task.removeProject` change project links. Workflows can copy or mirror these links, but TaskNotes owns the link rules and decides whether a task is blocked. These task dependencies are separate from the order of workflow steps. [0.1.4; [step catalog](https://github.com/callumalpass/tasknotes-workflows/blob/0.1.4/src/stepRegistry.ts#L254), [TaskNotes relationships](https://github.com/callumalpass/tasknotes/blob/4.13.8/docs/features/task-management.md#dependencies).]

**Vault actions.** Local action IDs are `notice.show`, `obsidian.openFile`, `obsidian.createNote`, `obsidian.appendNote`, `obsidian.updateFrontmatter`, `obsidian.moveFile`, and `workflow.stop`. They show a message, work with vault notes, or stop a run. `obsidian.createNote` makes an ordinary note, not a TaskNotes task; a `null` value in `obsidian.updateFrontmatter` removes a property. If that action edits a task note, it bypasses TaskNotes and omits the tag that identifies Workflows as the writer. These actions do not themselves require TaskNotes, though a workflow rule can still require it. [0.1.4; [step catalog](https://github.com/callumalpass/tasknotes-workflows/blob/0.1.4/src/stepRegistry.ts#L560), [Obsidian vault API](https://docs.obsidian.md/Plugins/Vault).]

**Run inspection.** A workflow card can dry-run even a disabled workflow. A dry run reads tasks and calculates inputs, while actions that would change data report their proposed changes instead. Run history shows success or failure, each step's result, original and calculated inputs, outputs, and errors; the log level controls how much is kept. A real run of a disabled workflow is skipped. These logs record runs separately from the task notes. [0.1.4; [engine](https://github.com/callumalpass/tasknotes-workflows/blob/0.1.4/src/workflowEngine.ts), [steps](https://github.com/callumalpass/tasknotes-workflows/blob/0.1.4/src/stepRegistry.ts#L800), [run logs](https://github.com/callumalpass/tasknotes-workflows/blob/0.1.4/src/runLogService.ts).]

**Plugin settings.** Settings control where workflows and their Base are stored, whether starter files are created, which triggers are enabled, and the interface language. They also set the shortest allowed interval, where run logs go, how much detail they hold, and how many entries are kept. Defaults are 60 seconds, 100 detailed runs per workflow, 1,000 summaries, and `inputs-and-outputs` logging. The settings loader enforces floors of 30 seconds, 10 detailed runs, and 50 summaries. Users can clear history and choose the system language or one of eight translations. [0.1.4; [settings](https://github.com/callumalpass/tasknotes-workflows/blob/0.1.4/src/settings.ts), [settings UI](https://github.com/callumalpass/tasknotes-workflows/blob/0.1.4/src/settingsTab.ts), [load/save](https://github.com/callumalpass/tasknotes-workflows/blob/0.1.4/main.ts#L167).]

## Definition and execution model

**Workflow file format.** New or edited workflow notes use `type: runtime_workflow`. The required fields are `id`, `version`, `name`, `enabled`, `triggers`, and `steps`; each trigger and step also has an ID and a named event or action with a version. Optional fields include `description`, `requires`, `vars`, `if`, `run`, and `x-` fields for extra data. Workflows puts schedule and editor details under `x-tasknotes`, including `format_version: 1` and `source: tasknotes-workflows`. Before saving, it checks the note against mdbase Runtime profile 0.2, which defines valid workflow files; the file's `version` is separate from plugin version `0.1.4`. [0.1.4; [schema guide](https://github.com/callumalpass/tasknotes-workflows/blob/0.1.4/docs/workflow-schema.md), [format converter](https://github.com/callumalpass/tasknotes-workflows/blob/0.1.4/src/workflowFormat.ts).]

**Minimal example.** This disabled manual workflow creates one TaskNotes task after it is enabled and run without dry-run mode. The workflow note stores `steps[0].input`; TaskNotes stores the resulting task in a separate Markdown file. Nothing in this example links tasks made by separate runs or checks for a duplicate before creating one. [0.1.4; [schema guide](https://github.com/callumalpass/tasknotes-workflows/blob/0.1.4/docs/workflow-schema.md), [create step](https://github.com/callumalpass/tasknotes-workflows/blob/0.1.4/src/stepRegistry.ts#L326).]

```yaml
---
type: runtime_workflow
id: create-review-task
version: 1.0.0
name: Create review task
enabled: false
triggers:
  - id: manual
    event: { id: tasknotes-workflows.manual, version: 1.0.0 }
    x-tasknotes: { type: manual }
steps:
  - id: create
    action: { id: task.create, version: 1.0.0 }
    input: { title: Review draft, status: open }
x-tasknotes: { format_version: 1, source: tasknotes-workflows }
---
```

**Step order.** Steps run in the order listed. A later step can read an earlier result through `steps.<id>.status`, `.output`, or `.error`. An `if` condition can skip a workflow or step; `for_each` repeats one step for a limited list of items. `run.on_error` chooses whether later steps run after a failure. Before a run, `requires.capabilities` checks whether TaskNotes has named abilities, but the engine does not check each step's `requires`; steps do not form a separate dependency graph. [0.1.4; [schema guide](https://github.com/callumalpass/tasknotes-workflows/blob/0.1.4/docs/workflow-schema.md), [engine](https://github.com/callumalpass/tasknotes-workflows/blob/0.1.4/src/workflowEngine.ts).]

**Calculated values.** An expression such as `{ $expr: "..." }` is a small calculation using Obsidian Bases formulas. It can read `workflow`, `trigger`, `event`, `vars`, earlier `steps`, the current `item`, `today`, and `now`. Plain strings stay unchanged; older `{{path.to.value}}` references still work, but a missing reference fails the step. A reference used alone keeps its original data type, while one inside longer text becomes text. The `task.query` step asks TaskNotes to find tasks using fields such as `where`, `sort`, `group`, `limit`, and `scope`. [0.1.4; [schema guide](https://github.com/callumalpass/tasknotes-workflows/blob/0.1.4/docs/workflow-schema.md), [template resolver](https://github.com/callumalpass/tasknotes-workflows/blob/0.1.4/src/template.ts), [query step](https://github.com/callumalpass/tasknotes-workflows/blob/0.1.4/src/stepRegistry.ts#L207).]

**Starting runs.** When the plugin loads or a workflow note changes, it reads valid workflow files and keeps their rules in memory. It then updates the events and manual commands it listens for. TaskNotes supplies task events, Obsidian supplies file and workspace events, and a timer checks schedules. A matching event starts a run with a new random run ID (`runId`), but adds no lasting run record to a task note. Disabling or deleting a workflow stops future automatic runs after reload; earlier task and file changes remain. [0.1.4; [repository](https://github.com/callumalpass/tasknotes-workflows/blob/0.1.4/src/workflowRepository.ts), [watchers](https://github.com/callumalpass/tasknotes-workflows/blob/0.1.4/main.ts#L463), [scheduler](https://github.com/callumalpass/tasknotes-workflows/blob/0.1.4/src/scheduler.ts), [engine](https://github.com/callumalpass/tasknotes-workflows/blob/0.1.4/src/workflowEngine.ts).]

**Other app actions.** Workflows runs its TaskNotes actions itself. For an action owned by another app, optional `mdbase-obsidian` sends a named request to that app and can receive its events. The request is a contract with an agreed ID and version; `provider.application`, `provider.implementation`, or `provider.instance_id` can select which app handles it. This link needs permission and exactly one matching app, and the run log keeps the request and result. Workflows also offers `tasknotes.workflow.run` version `1.0.0`, which lets a permitted app start a workflow by `workflow_id`. [0.1.4; [README](https://github.com/callumalpass/tasknotes-workflows/blob/0.1.4/README.md), [bridge](https://github.com/callumalpass/tasknotes-workflows/blob/0.1.4/src/tasknotesBridge.ts), [provider](https://github.com/callumalpass/tasknotes-workflows/blob/0.1.4/src/interopProvider.ts).]

## Configuration to stored data

**Task creation.** Set a trigger and a `task.create` step with `input.title` and optional status, priority, dates, details, or other TaskNotes creation fields. Workflows stores the action as `action: {id: task.create, version: 1.0.0}` plus its `input`. At run time, it fills in calculated values and calls `api.tasks.create`; TaskNotes chooses the task folder, applies defaults and field-name settings, and writes a separate Markdown note. The step returns the new task and `path` for later steps. Workflows does not add its workflow or run ID to the task, so it does not group tasks made by separate runs or prevent repeat creation. [0.1.4; [create step](https://github.com/callumalpass/tasknotes-workflows/blob/0.1.4/src/stepRegistry.ts#L326), [TaskNotes creation API](https://github.com/callumalpass/tasknotes/blob/4.13.8/docs/javascript-api.md#task-operations), [TaskNotes task type](https://github.com/callumalpass/tasknotes/blob/4.13.8/src/types.ts#L501).]

**Task property mapping.** Set `input.task` to the task path and put changes inside `input.patch` for `task.patch`. Use TaskNotes field names such as `status`, `priority`, `due`, `scheduled`, `projects`, and `blockedBy`, even if the vault uses different YAML property names. TaskNotes maps those names to the user's chosen keys; for example, `scheduled` can be stored as `do`. Put other properties in `patch.customFrontmatter`; `null` removes one. Changes later made to the task do not change the workflow rule. [0.1.4; [schema guide](https://github.com/callumalpass/tasknotes-workflows/blob/0.1.4/docs/workflow-schema.md#expressions), [patch step](https://github.com/callumalpass/tasknotes-workflows/blob/0.1.4/src/stepRegistry.ts#L340), [TaskNotes core concepts](https://github.com/callumalpass/tasknotes/blob/4.13.8/docs/core-concepts.md).]

**Dependency storage.** For `task.addDependency`, set the dependent `task` and a blocker with `uid` (link to the blocker), `reltype` (link type), and optional `gap` (time delay). `task.removeDependency` removes a blocker by its `uid`; `FINISHTOSTART` means the blocker finishes before the dependent task starts, and `P1D` means a one-day gap. TaskNotes stores these values in the dependent task's `blockedBy` list; for example, `uid: "[[Operations/Order hardware]]"`, `reltype: FINISHTOSTART`, and `gap: P1D`. TaskNotes works out the reverse list rather than storing it. Its UI defaults to `FINISHTOSTART`, and it treats unfinished blockers as blocking regardless of `reltype` or `gap`. [0.1.4; [dependency steps](https://github.com/callumalpass/tasknotes-workflows/blob/0.1.4/src/stepRegistry.ts#L475), [TaskNotes dependency guide](https://github.com/callumalpass/tasknotes/blob/4.13.8/docs/features/task-management.md#dependencies).]

**Project relationships.** Set `projects` when creating or changing a task, or use `task.addProject`. TaskNotes stores project links in YAML, such as `projects: ["[[Q1 Planning]]"]`. A task linked to another task as a project is treated as its subtask; `task.parents` and `task.subtasks` ask TaskNotes to find those links. Starter workflows can then copy selected fields from a parent or mirror later changes. Project links and blocking dependencies are separate relationships. [0.1.4; [relationship steps](https://github.com/callumalpass/tasknotes-workflows/blob/0.1.4/src/stepRegistry.ts#L254), [TaskNotes task guide](https://github.com/callumalpass/tasknotes/blob/4.13.8/docs/features/task-management.md#projects-and-subtasks).]

**Run records.** Each run gets a random run ID (`runId`), a workflow ID (`workflowId`), its source path, trigger, status, times, and step results. By default, `.obsidian/plugins/tasknotes-workflows/runs/history.jsonl` holds one summary per line; details go in `.obsidian/plugins/tasknotes-workflows/runs/workflows/<workflow-id>/<runId>.json`. The `runLogRoot` setting can move these files, and separate limits control how many summaries and details remain. The logs link runs to workflow rules, but generated tasks get no automatic link back to a run. [0.1.4; [run log service](https://github.com/callumalpass/tasknotes-workflows/blob/0.1.4/src/runLogService.ts), [engine](https://github.com/callumalpass/tasknotes-workflows/blob/0.1.4/src/workflowEngine.ts).]

## Compatibility, limits, and discrepancies

**Older file formats.** Version 0.1.4 still reads older `type: tasknotes-workflow` and `type: workflow` files with `schemaVersion: 1`. Saving a workflow now writes `type: runtime_workflow`; simply loading an old file does not convert it. The migration command previews changes and checks that the files have not changed before writing. It saves backups under `.obsidian/tasknotes-workflows/workflow-migrations/` and restores earlier files if a later write fails. The TaskNotes [website guide](https://tasknotes.dev/obsidian/companion-plugins/tasknotes-workflows/) still shows the older format, while the plugin's versioned schema guide shows the new one. [0.1.4; [schema guide](https://github.com/callumalpass/tasknotes-workflows/blob/0.1.4/docs/workflow-schema.md#compatibility-and-migration), [migration source](https://github.com/callumalpass/tasknotes-workflows/blob/0.1.4/src/workflowMigration.ts).]

**Accepted versus executed.** The file rules accept settings that the 0.1.4 runtime does not carry out. These include `run.concurrency.policy: queue` or `replace`, `run.limits.timeout`, trigger `debounce` and `minimum_interval`, plus cron `catchUp` and `timezone`. During a run, only `allow` permits overlap; every other concurrency value skips a second active run, so `queue` does not queue and `replace` does not replace. Cron and interval checks use a one-minute timer and the device's local clock; closed-Obsidian runs are not replayed. The guide also shows `run.idempotency` and trigger-level `if`, but the plugin drops them before execution. [0.1.4; source verified: [format converter](https://github.com/callumalpass/tasknotes-workflows/blob/0.1.4/src/workflowFormat.ts), [engine](https://github.com/callumalpass/tasknotes-workflows/blob/0.1.4/src/workflowEngine.ts), [scheduler](https://github.com/callumalpass/tasknotes-workflows/blob/0.1.4/src/scheduler.ts), [schema guide](https://github.com/callumalpass/tasknotes-workflows/blob/0.1.4/docs/workflow-schema.md).]

**Other edge cases.** One TaskNotes change can emit several events, and several triggers may start separate runs. Workflows normally ignores task events caused by its own writes; `allowSelfTrigger: true` removes that check and can cause loops. The generated Base filter lists only older workflow types, while its card view reads the workflow folder directly. Reading-mode note cards also check only one older type; their visible behavior with current-format notes needs a live Obsidian check. Saving through the editor sets the workflow file's `version` to `1.0.0`, even if the source had another version. [0.1.4; source verified: [scheduler](https://github.com/callumalpass/tasknotes-workflows/blob/0.1.4/src/scheduler.ts), [Base generator](https://github.com/callumalpass/tasknotes-workflows/blob/0.1.4/src/defaultWorkflowsService.ts#L68), [note card](https://github.com/callumalpass/tasknotes-workflows/blob/0.1.4/src/workflowNoteCard.ts#L292), [format converter](https://github.com/callumalpass/tasknotes-workflows/blob/0.1.4/src/workflowFormat.ts#L72).]

**Sample mismatches.** The editor's `task.addDependency` sample uses `{ path: "Tasks/example.md" }`. TaskNotes' dependency data instead uses `uid` for the blocker and `reltype` for the link type. I did not test the sample in the editor, so its effect is uncertain. The TaskNotes website describes `task.set` as a one-field action, but the 0.1.4 code treats it as `task.patch` with an `input.patch` object. These differences do not establish a second supported dependency format. [0.1.4; source verified: [step catalog](https://github.com/callumalpass/tasknotes-workflows/blob/0.1.4/src/stepRegistry.ts#L363), [TaskNotes dependency type](https://github.com/callumalpass/tasknotes/blob/4.13.8/src/types.ts#L448), [TaskNotes mutation](https://github.com/callumalpass/tasknotes/blob/4.13.8/src/api/TaskNotesAPI.ts#L2163), [TaskNotes site](https://tasknotes.dev/obsidian/companion-plugins/tasknotes-workflows/).]

**Evidence limits.** “Documented” means an official guide states the behavior; “source verified” means the 0.1.4 Workflows or 4.13.8 TaskNotes code shows it. “Inconclusive” means the evidence does not settle a point, such as live Base rendering or permissions for other apps. I found no minimum compatible TaskNotes version or lasting link from a generated task back to its run. I checked the code needed to explain these features, not every line of either project.

## Accepted versus executed: expanded behavior

**Configuration stages.** A schema lists valid settings in a YAML workflow file; passing that check only means the file has an accepted shape. A parser then turns the file into the plugin's working rule. A scheduler decides when to start a run, and an execution engine carries out its steps. In 0.1.4, some accepted settings reach the working rule but are never read during a run. Other settings appear in the schema guide but disappear when the file is converted. [0.1.4; documented and source verified: [format conversion](https://github.com/callumalpass/tasknotes-workflows/blob/0.1.4/src/workflowFormat.ts#L36), [parser](https://github.com/callumalpass/tasknotes-workflows/blob/0.1.4/src/workflowParser.ts#L44), [scheduler](https://github.com/callumalpass/tasknotes-workflows/blob/0.1.4/src/scheduler.ts#L26), [engine](https://github.com/callumalpass/tasknotes-workflows/blob/0.1.4/src/workflowEngine.ts#L34).]

**Overlapping runs.** Concurrency means two runs active at once. The parser accepts `run.concurrency.policy` values `skip`, `queue`, `replace`, and `allow`, but the engine only tests for `allow`. With `allow`, another run starts; with any other value, it is logged as `skipped`, so `queue` does not wait and `replace` does not stop the first run. `run.concurrency.group: global` makes workflows share one overlap group; other group values are paired with the workflow ID. The parser also keeps `run.limits.timeout: 30s`, but the engine does not use it to stop a long run. [0.1.4; source verified: [policy parser](https://github.com/callumalpass/tasknotes-workflows/blob/0.1.4/src/workflowParser.ts#L514), [overlap check and group key](https://github.com/callumalpass/tasknotes-workflows/blob/0.1.4/src/workflowEngine.ts#L71), [run logging](https://github.com/callumalpass/tasknotes-workflows/blob/0.1.4/main.ts#L279).]

**Event controls.** A trigger's `debounce` would combine events that happen close together; `minimum_interval` would limit how often it runs. The parser keeps them as `debounce` and `minimumInterval`, and saving writes them back, but the scheduler checks neither value. Each matching event is considered separately, subject to other filters and the overlap rule. The guide also shows a trigger-level `if` condition, but conversion drops it before scheduling; an editor save omits it too. Workflow-level and step-level `if` conditions do reach the engine. [0.1.4; documented and source verified: [schema guide](https://github.com/callumalpass/tasknotes-workflows/blob/0.1.4/docs/workflow-schema.md#conditions), [trigger conversion](https://github.com/callumalpass/tasknotes-workflows/blob/0.1.4/src/workflowFormat.ts#L125), [event dispatch](https://github.com/callumalpass/tasknotes-workflows/blob/0.1.4/src/scheduler.ts#L208), [guard execution](https://github.com/callumalpass/tasknotes-workflows/blob/0.1.4/src/workflowEngine.ts#L96).]

**Scheduled runs.** Cron is a five-part time pattern, such as `0 9 * * *` for 9:00 each day. The plugin checks schedules when it loads and about once a minute afterward; cron uses the device's local clock even when `x-tasknotes.timezone` names another zone. For intervals, it uses the longer of `x-tasknotes.every` and the plugin setting `minIntervalMs`, but a 30-second minimum cannot make a one-minute timer check twice per minute. The scheduler keeps last-run times only in memory, starts an interval when no time is recorded, and does not use `x-tasknotes.catchUp`. Thus an interval may run once when Obsidian reopens, but missed runs are not replayed. **Duplicate protection.** Idempotency means recognizing a repeated request so it is carried out only once. The guide shows `run.idempotency.key`, but conversion drops it; the engine gives each run a fresh ID and does not check the key. An editor save omits `run.idempotency` too. An action sent to another app has its own automatic key for that one request, which does not prevent repeated workflow runs. By comparison, `run.limits.max_items` does limit a `for_each` list, and `run.on_error` does control what happens after a failed step; these findings come from code, not live timing tests.
